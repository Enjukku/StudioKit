## 1. How I checked

| Step | What I did |
| --- | --- |
| Source order | The register URL first. If the studio page could not be read, a copy on another official domain (publisher partner pages, Valve's Steam Community posts, Valve's patch-notes feed, Supercell's own earlier post). Only then press that quotes the studio, used to locate the post and read its text, never as the studio's number when the studio page was readable. |
| Tool limit | WebFetch returns a model extract of the page, not raw text. For every number, date and quote that matters I asked a second time with a different prompt and kept only what both extracts agreed on. Quotes below are 15 words or fewer and come from those extracts. Search-engine summaries were used only to find URLs; none is cited as evidence. |
| Unreadable primaries | `x.com` (HTTP 402), `fortnite.com` and `epicgames.com` (403), `web.archive.org` (blocked by the tool), `genshin.hoyoverse.com` (script shell, no body), `bungie.net` (script shell), `dota2.com/news` (script shell), `minecraft.net` (repeated timeouts). | Dota | Valve's own patch feed (`dota2.com/datafeed/patchnoteslist`) and Valve's Steam Community announcements (Steam news API, appid 570) were readable and are first-party. |
| Verdicts | confirmed = the source says what the paper says, within the paper's scope. corrected = the source differs in a way that changes wording, scope or a date; the right version is given. unverified-kept-with-label = could not read the studio text; press agrees or nothing else found; keep only with the label. dropped = no source. |
| Tag check | The paper's tags: VERIFIED = a published schedule, date or count the studio states as fact; EXPERIENCE = the studio's own account or result. Studio-stated results (Supercell revenue, Riot rationale) stay EXPERIENCE. A published schedule is VERIFIED only as a promise, not as proof the promise was kept. |
| Date arithmetic | Mine, from the dates shown. Labeled "my arithmetic". |

## 4. Cross-case lessons the evidence still supports

Mechanism only; none is a benchmark. Each is one studio's report or plan.

| Lesson | FG ids |
| --- | --- |
| A fixed weekly release-day appointment can cost the team and the players (late-day finishing, awkward time zones); one studio moved to a flexible schedule with announced times. It did not say capacity was exceeded. | FG-01 |
| A public cadence line on a listing is a promise, not proof that the promise is kept or what it costs. | FG-04, X-09 |
| A multi-week event can carry several beats without new systems: the Adopt Me festival ran 4 weeks with weekly updates. | FG-02 |
| Scale counts (players, hours) say nothing about return; the Fortnite post gives neither. | FG-05 |
| A returning-content event can be delivered as weekly phases through a month. | FG-06 |
| Balance less often in a healthy mode so players have time to discover builds: one mode, one plan. | FG-09 |
| Drip-feeding a couple of units every couple of weeks did not move sentiment or playtime in one TFT set; bundling them cost heavy workload. | FG-12 |
| Shorter pre-release testing, driven by an outside date, cost day-one balance and let bugs through. | FG-11 |
| A heavily produced collaboration event can underperform when execution has faults (overpowered limited unit, a free-release mistake, off-theme store, a currency bug); the studio saw the trend in January and could not turn fast enough. | FG-14 |
| An early lift in one group's playtime can normalize while another group's participation falls. | FG-15 |
| A public experiment can split players (80/20 on quest cadence) with no result stated at launch. | FG-16 |
| Interval plans are historical (Genshin 2.7 six weeks, Overwatch nine weeks): they show intent at a date. | FG-17, FG-19 |
| An annual story arc plus a returner catch-up section is one way to make separate patches legible. | FG-20 |
| A version's date can be read as a release date when the studio states it; a release interval is not development time. | FG-18, FG-21 |
| An event can pay its currency win or lose, and the same update can fix reward bugs and add reward information. | FG-22 |
| Packaging can be revised (Mini-Sets on a break, Class Sets after each expansion); a plan is not delivery. | FG-25, FG-27 |
| When replacing a progression system, state what happens to the old level (King Tower level never lowered). | FG-26 |
| A studio can watch several feedback channels and still not report weights or results. | FG-30 |
