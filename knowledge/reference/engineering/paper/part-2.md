# Paper part 2: engine-first rules, phone budgets, tests and tools, review method

## 0. How to read this note

- `pl.NNN` = paper line number. `Q00` = the paper's own proposed policy (always OPINION). Source ids (A, C, L, R, T) are the paper's register ids, kept exactly. Register aliases: `C06 = T01` (Wube Friday Facts #366), `L01 = T04` (Luau 0.743), `L16 = R11` (native code gen), `L19 = R06` (Improve performance).
- Tags are the paper's own. The paper states it ran no code, test, benchmark or device. Every example, procedure and number marked OPINION is a proposal; none was tested. "Accessed 2026-10-21" is an access date, not a publication date (the paper says so; keep it).
- Roles: arch = architect, feat = feature-builder, quick = quick-builder, rev = reviewer, perf = performance-engineer, qa = qa-lead, all.
- Kit status: NEW / ALREADY-IN-KIT / CONFLICTS-WITH-KIT, checked against `.agents/skills/{architecture,code-review,performance,data-saving,networking-security,studio-mcp}`, `performance/references/{budgets,measure,fixes}.md`, `code-review/references/{testing,luau-current}.md`, `rules/anti-overengineering.md`, `rules/messages.md`. Skills outside that list (analytics, ui-basics, platform-policy, animation) were not read; statuses that touch them say so.
- A `★` after an id means: check this claim first (it would change what an agent does, or the kit disagrees with it).
- Evidence convention of §5 (pl.452): VERIFIED = the cited official source documents the capability; it does NOT mean the paper benchmarked it.
- The paper's §5 table has a "when custom work is justified" column that is always OPINION Q00, 2026-10-21; the "built-in capability" column is VERIFIED. Both are kept separate below.

## 5. Checklists and templates in the paper (paraphrased, fields in full)

### 5a. Engine-first gate (pl.454)
Questions the feature builder answers before adding a replacement service: (1) Which built-in did I evaluate? (2) What concrete requirement did it fail? (3) How will the replacement be measured? Also state, per need, what is custom (the "when custom work is justified" column in P202-P218).

### 5b. Performance acceptance record (pl.503)
Fields: exact device and OS; Roblox version; place version; quality settings; player/content scenario; session duration; measurement method; trace location. Plus three separate entries: frame target, project acceptance threshold, measured result. If no physical device: status = blocked or unverified.

### 5c. Project-number procedure (pl.520)
1. Pick a representative vertical slice and the lowest supported phone. 2. Sweep one stressor at a time (visible population, active physics, ability effects, UI updates, network activity). 3. Hold other conditions stable. 4. Save the trace at the point the target first fails. 5. Set a lower operating threshold with an explicit margin; record the reason. 6. Re-run when content or engine versions change. 7. Treat the numbers as belonging to this project, device and workload.

### 5d. Performance evidence packet (pl.532)
Reproducible scenario; baseline capture; changed capture; largest cost category; proposed cause; actual change; observed outcome. Memory snapshots at equivalent lifecycle states.

### 5e. Test result record (pl.567)
Commit; artifact hash; runtime/version; scenario; actor; seed when applicable; expected result; observed result; raw log; verdict in {PASS, FAIL, BLOCKED, NOT RUN}.

### 5f. CI on every candidate commit (pl.587)
Install pinned tools and packages -> strict analysis and pure tests -> build the test place -> run the server-side regression suite on that exact artifact -> keep machine-readable result and logs. Client tests fitting the change remain required. No production deployment credentials or production saves reachable by the test process.

### 5g. Save-migration fixture checklist (pl.589)
Versioned anonymised fixtures with explicit expected output for: missing optional fields; boundary amounts; an old valid inventory; interrupted-migration markers; already-migrated data. Run on a deep copy; compare exact economic fields and required retained unknown fields; run again and check repeat behaviour; then test the persistence adapter in an isolated environment; never auto-update the expected fixture.

### 5h. Lifecycle regression check (pl.591)
Track owned connections and tasks; repeat create/use/destroy; assert owned registrations return to baseline; sample memory and instance trends after a settling period; do not gate on an exact byte count.

### 5i. Test-count guidance (pl.595)
No number. Use: requirement-to-evidence matrix (every stated behaviour and material failure mode has an observable check at the boundary where it fails); known-bug regressions; intentional fault challenges. If removing a critical check leaves a known-faulty candidate's verdict unchanged, improve the evaluator. Matrix columns are not specified by the paper.

### 5j. Multi-actor scenario (pl.583)
Smallest actor count that exposes the failure; scenarios: contention, late join, disconnect/rejoin, respawn; an explicit harness that knows each actor; a statement of which part needed Studio UI control.

### 5k. Reviewer input packet (pl.619)
Exact base revision; proposed revision; task contract; changed files; touched APIs; test commands; test outputs; known omissions. Order: own pass over change + call sites first, builder's self-review second, then reconcile discrepancies.

### 5l. Finding shape (pl.621)
Class (BLOCKER / REQUIRED / OPTIONAL). For BLOCKER and REQUIRED: affected location; observed or predicted failure; relevant contract clause; executable reproduction or a clearly described evidence gap.

### 5m. Review comment shape (pl.625)
Tie the change to behaviour and to a check; name what to do or what contract to change. Avoid vague "more robust" and speculative genericity. (Example in the paper is an untested illustration.)

### 5n. Failure classification (pl.629)
Production defect / test defect / fixture defect / environmental failure / unverified hypothesis. Runner failed to launch = RUNNER FAILED. Design vs expected-value conflict = owner decision in plain language.

### 5o. Review end conditions (pl.635)
Required checks pass on the exact candidate revision; non-optional findings closed with evidence; scope changes reconciled; remaining uncertainties accepted or deferred by the appropriate authority.

### 5p. Role split without a human engineer (pl.641)
Builder: implementation + visible task tests. QA: acceptance run + hidden fixtures. Reviewer: review decision. Performance: benchmark comparison on measured hot paths. One session may cover low-risk roles in sequence; it may not rewrite hidden acceptance criteria after a failure.

### 5q. Hidden-evaluation rule (pl.643)
Builder workspace excludes withheld fixtures, oracle, grader config, stored baselines; QA reveals failed requirement category, not every hidden input; no isolation = say "visible to the builder".

### 5r. Release packet (pl.645)
What changed for players; what passed; what could not be checked; whether stored data or paid transactions are affected; what changed in device performance; how to stop or revert. Owner (designer) is release authority.

### 5s. Acceptance record pin (pl.548)
Name the exact APIs and configuration a feature needs; recheck their current docs before implementation.

The "task contract / acceptance packet / rework record" templates are in the paper's §9 and later, outside this range.

## 6. Contradictions and unknowns

### 6a. Inside the paper
1. Blocked vs not run. §6 (pl.516) says record physical-device acceptance as "blocked or unverified"; §7 (pl.567) defines BLOCKED and NOT RUN as different verdicts. The paper never maps "no device" to one of them. Default: BLOCKED (could not run), NOT RUN (was not attempted).
2. Review tension, acknowledged by the paper (pl.613): generic Claude Code guidance recommends fresh-context adversarial review; Opus 5 guidance recommends dropping blanket verification. The paper's resolution (broad discovery first, strict filter second, measure the extra pass) is OPINION and untested.
3. Citation mismatch (pl.613): the "5.5 starting point" is attributed to A03, whose register quote is about reserving xhigh/max effort, not about verification. A04's quote is about over-verification on Opus 5. Check before relying on the claim.
4. Human reviewer: C08 (Epic) escalates irreversible changes to a human, and the paper says to obtain "qualified human engineering review" when agents cannot support a judgement (pl.645), while the whole studio is agents plus a non-programmer designer (pl.611). The paper does not say who the human is.
5. Server memory: 3 GB guideline vs 6.25 GiB + 100 MiB x players at 50 % (pl.546). The paper itself says they are not equivalent and prefers the percentage.
6. MicroProfiler network: page wording on desktop dumps vs "low detail level" for mobile (pl.528); the paper leaves it open.
7. Initial speed budgets "60 s / 10 min / 30 min" (pl.602) appear in the rule table only; they conflict in spirit with the section's own "no universal number" stance, but are marked OPINION and "not benchmark". Not stated whether the 60 s covers pure tests only.
8. Server Authority wording: "full release confirmed in the July 10 recap" (pl.463) with a note that older beta announcements are stale; the paper separately warns (pl.548) that a base release does not confer full release on extensions. It does not list which Server Authority extensions are still beta.
9. Native code: "not a general phone switch" (pl.558) while L17 (roadmap, 2026-05-08, in the register) says Android native code gen was "Ongoing -> Mid 2026". The paper's section 4 (outside this range) may address this.
10. Register ids: `R06` and `R11` appear as aliases (`L19`, `L16`) in the register; fine, but the section text uses R-ids only.
11. The Studio MCP table (pl.581) names `execute_luau`, `start_stop_play`, `get_console_output`, `screen_capture` and "simulated input" but not the kit's other tools (`character_navigation`, `subagent` etc.); the paper does not say the list is complete.

### 6b. Paper vs kit
1. `budgets.md` server memory gate mixes "<= 3,000 MB" and "< 50 %" (P248). Paper: do not present 3 GB as a ceiling. [soft conflict]
2. `testing.md:92` says run-in-roblox 0.3.0 is from 2020; paper says the year cannot be inferred from GitHub's date display (P257). [minor factual conflict]
3. `anti-overengineering` rule 20 / `code-review` V-11 stop after 3 review rounds vs paper's "no universal cap" (P279). [soft conflict; different purpose: escalation vs pass condition]
4. `code-review` V-12 severity (Critical/High/Medium, lower not reported) vs BLOCKER/REQUIRED/OPTIONAL (P274). [vocabulary conflict]
5. `performance/references/fixes.md` collision-fidelity list omits Tunable (P224). [obsolete-checklist gap]
6. `fixes.md:13` "pool instances created and destroyed often" vs paper's "measure allocation and teardown, no unlimited pool by default" (P246). [mild tension]
7. `budgets.md` budget numbers (floor phone 30 FPS, memory MB, remote rates, scripts p95 3 ms) are unsourced in the paper, which says no such universal number exists (P229-P234). They are labelled PROPOSAL in the kit, so no conflict while the label stays; every agent must repeat it.
8. Convention-based test integrity in `testing.md` ("builder does not change expected results") vs paper's enforced workspace separation (P282). [tension]
9. Test vocabulary: kit labels (gate-verified / MCP-verified / owner-confirmed / not verified) vs PASS / FAIL / BLOCKED / NOT RUN (P251). Not in conflict, but two vocabularies need a mapping.
10. Server Authority date: kit "live 2026-07-09" (`networking-security`) vs paper "July 10 recap" (P208).
11. Kit-only figures with no paper basis: Open Cloud Luau Execution <= 5 min per task, 100 create/destroy cycles, `StudioTestService:ExecuteMultiplayerTestAsync`, UnreliableRemoteEvent 1,000-byte limit. Not contradicted; they need their own docs-mirror source.
