## 5. Checklists and templates in this range (all fields paraphrased)

### 5a. Task contract (line 664; example line 666)
Nine fields: (1) existing behavior; (2) intended change; (3) examples with expected outcomes; (4) relevant engine or library APIs; (5) files or call paths likely affected; (6) allowed scope; (7) explicit non-goals; (8) checks that accept the change; (9) what the agent may decide alone versus what the designer must choose. Proportional to risk. The reward example (untested template) fixes: who is eligible; no double grant on reprocessing; a leave-before-cutoff case settled by an attached design example; the existing reward entry point is used; no new reward framework and no unrelated item edits; a replayable test for the existing bug; the required integration check; the amount and eligibility rule come from the designer.

### 5b. Architect decision record (line 668)
Route through existing code; the actual constraint requiring change; rejected alternatives when consequential; what the builder must not change. Never a new subsystem to justify the role. For a quick patch: one short note.

### 5c. Responsibility and hand-off matrix (lines 674-680)
| responsibility | produces | hands off when | must not |
| --- | --- | --- | --- |
| Architect | narrow behavior contract and change route | intent and material constraints resolved | invent future requirements; replace a local fix with a framework |
| Feature builder | implementation, visible checks, change explanation | candidate runnable and known failures disclosed | rewrite acceptance rules to fit the output |
| Quick builder | small patch with the same applicable correctness gates | the narrow patch meets its contract | skip required checks because the change is called quick |
| Reviewer | prioritized findings and disposition | required findings have evidence-based resolutions | treat taste as a blocker without a settled rule |
| Performance engineer | baseline and candidate comparison for relevant workloads | measurements comparable and limits explained | claim a speedup from source inspection alone |
| QA lead | acceptance evidence and withheld evaluation results | exact candidate passed required checks or is clearly blocked | let the builder edit hidden oracles and report self-approval |

### 5d. Evidence states (line 684)
READY, IMPLEMENTING, CHECKS RUNNING, BLOCKED, REVIEWING, ACCEPTED, RELEASED (suggested). Store base and candidate revision with every transition.

### 5e. Builder-to-reviewer change manifest (line 686)
Requirement ids addressed; files changed; public behavior or API shape changed; external dependencies added or updated; test commands and return status; actual environment; performance-sensitive paths touched; unresolved questions; generated content needing inspection. Link logs. Missing check: "NOT RUN" with the reason.

### 5f. Builder stop-and-decide return (line 688)
Unsupported assumption; source or reproduction; smallest feasible alternatives; player-facing tradeoff. Stop the dependent work; no silent substitute; no custom system without saying why the built-in is not enough.

### 5g. Concurrency and escalation rules (lines 692, 694)
Parallel only for outputs that combine without competing edits; one integrating owner per candidate revision; each contributor declares changed assumptions; start with the least coordination; escalate on a concrete uncertainty (type-system behavior, native-code hot path, persistence API constraint, rendering bottleneck, runner limitation).

### 5h. Small change and scope growth (lines 698, 700)
Small = narrow behavioral purpose + comprehensible set of callers + checks that can show the purpose was met. Record affected behavior and dependencies. Necessary work (blocks accepted behavior) needs an explicit contract update; opportunistic work is deferred; optional cleanup stays separate unless needed for correctness or testability.

### 5i. Owner acceptance packet (line 704)
Six questions: what will players notice; what behavior was checked; what was not checked; did performance or resources change on the named target; does it touch persistent or paid state; what should the owner do now. Machine-readable evidence attached separately. For paper-only or inspection tasks, say so (line 706).

### 5j. Rework record (lines 725, 745)
Task and candidate revision; intended behavior; first observed failure; how found; exact reproduction or saved fixture; wrong assumption; repair; new prevention mechanism; the original failed result when safe. Keep the original acceptance contract with the record (line 731). Example (untested): in-place sort of a shared rewards table.

### 5k. Cause taxonomy (line 729)
Requirement ambiguity; missing repository context; incorrect API assumption; incorrect algorithm; omitted integration behavior; lifecycle/resource failure; performance regression; test-oracle error; environment or runner failure; scope expansion; review churn. Primary category only with evidence; secondary factors allowed; UNKNOWN allowed. Separate from "changed requirement" and "platform change" (line 731).

### 5l. Prevention choices and rule shape (lines 735, 737)
Failure type to prevention: deterministic calculation to a small behavioral regression case; API availability to a pinned documentation reference or executable capability check; unclosed connection on repeated screen opens to an instrumented lifecycle scenario; speculative framework to a change-review question requiring a current caller or measured need. Persistent rule = trigger + required action + verification; promote only if scope clear, behavior stable, would have prevented the mistake; retire when obsolete or superseded, keeping date, scope, reason and superseding decision.

### 5m. Rework measurement definitions (lines 751-755)
Metrics: first-pass acceptance, accepted task count, reopen rate, escaped defects, time to accepted result, cost of required runs. First-pass acceptance (proposed): the first submitted candidate passes the frozen acceptance suite and review criteria without a code revision. Report numerator, denominator, task mix, model identifier, tool configuration, exclusions. Track failed, blocked, abandoned and reclassified separately; count all implementation revisions and tool-driven repairs for end-to-end rework; keep "first submitted candidate" apart from "first generated implementation". Test a new rule on a fixed slice of like tasks, keep the old baseline, report side effects, no universal sample size or threshold.

### 5n. Evaluation setup checklist (lines 770-774, 784-788, 825-827)
Same frozen starting commit, acceptance contract, tool versions, time/token budget for every candidate. Save initial prompt, model identifier, harness configuration, tool permissions, outputs, diff. Freeze the hidden evaluator before the builder starts; evaluator files and verdict writer outside the builder's writable environment (a test-only agent with the same writable checkout does not count). Report first-attempt success (first submitted candidate before hidden-test feedback) separately from eventual success; record repairs, time, tokens/cost, unrelated changes, regressions, missing evidence. Include a valid "no change needed" task. Compare against the existing team on the same held-out tasks. Representative tasks per role; clean controls; held-out variants; repeats when nondeterminism matters; publish raw counts, categories, uncertainty, failures, costs; grow the set around observed gaps. Reviewers scored on critical-fault recall and false blockers separately; builders on correctness, preservation and cost. Block or reduce when repair cannot settle a material failure; budget is not a waiver. Never PASS for skipped, blocked, timed-out or never-launched runs.
