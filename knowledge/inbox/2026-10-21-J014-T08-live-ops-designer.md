# Lessons: live-ops designer, first test on a synthetic live game (J014-T08)

| # | What happened | Lesson |
| --- | --- | --- |
| 1 | Splitting the count window at the 1.1.1 release showed purchase, save-loss and Dust-surplus reports all start after that build | Count before and after every build or event inside the window |
| 2 | "More rewards" and "nothing after the pond" read against the analyst's Orchard numbers became a findability problem, not a content request | Read solution-shaped feedback against behaviour data before ranking |
| 3 | The Spark ledger balanced exactly | A balanced surplus is an economy design gap, not an incident; check the ledger before calling currency "exploitable" |
| 4 | A script compared 132 cited counts with the tool output: 0 mismatches | Cross-check every cited count mechanically before handing back |
| 5 | Shipping the event dormant in an earlier release window kept the release-to-start rule | Put the release window and the start gate in the event design |
| 6 | The biggest problem (new phone players stopping at the lantern step) was almost invisible in feedback because the in-game form appeared only after 30 catches | A feedback prompt that waits for engagement cannot hear early quitters; the funnel is the evidence there |
| 7 | No scope estimates were possible in a single-agent test | Label options "pre-estimate" and keep dates uncommitted |
