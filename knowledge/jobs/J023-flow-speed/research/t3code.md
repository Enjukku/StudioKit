# T3 Code: what it is and what the Studio Kit can take from it

Question (J023-flow-speed): jobs use too many tokens and take too long. Which T3 Code mechanisms help, and which do not apply?
Labels: **[doc]** = stated on the page cited; **[code]** = read in the source file cited; **[inf]** = my inference. The GitHub pages show no line numbers to the reader, so citations name the file and the function or section.

## 1. What T3 Code is

T3 Code is an open-source "agent harness control surface": a web app, an Electron desktop app and mobile apps that control coding agents running on your own machine through a local or remote server [doc: https://github.com/pingdotgg/t3code, README]. It wraps the CLIs of Claude Code, Codex, Cursor, Grok Build, OpenCode and Google Antigravity [doc: same page]; the Claude side runs on the Claude Agent SDK [code: https://raw.githubusercontent.com/pingdotgg/t3code/main/apps/server/src/provider/ClaudeTurnTokenUsage.ts, header]. It is for developers who want to run several agent threads (each in a project folder or a git worktree), approve actions, review diffs and open pull requests from one UI [doc: docs/user/source-control.md, docs/user/permission-modes.md]. Main parts: `apps/server` (provider adapters, an event-sourced orchestrator in `orchestration-v2`, checkpointing, git, usage), clients on a shared `packages/client-runtime`, and an MCP endpoint so outside agents can start and message threads [doc: https://github.com/pingdotgg/t3code/blob/main/docs/internals/overview.md; docs/user/outside-agents.md]. The README says the project is "very very early". It is a **control surface for one agent per thread**, not a multi-role job engine: I found nothing that plans jobs, assigns roles or chains reviewers (absence in the pages read; [inf]).

## 3. Ranked takeaways

1. **Compact (or restart) inside the cache window, never after it.** Change: add one rule to the lead's session habits and, if the owner enables it, a hook. At a stage end or before waiting for an owner gate, if context is past the compaction floor and the cache is still warm, compact or start the next stage fresh from the job files; do not let a session sit idle past the cache expiry and then resume the 300-600 k context. Never compact twice in one idle spell. Cost: low (rule text in `rules/assistants/claude.md` Session size and the orchestration skill; a hook is a small script). Honest limit: T3 can send `/compact` on a timer; we cannot, so the lead must do it before the gate pause [inf]. Verify the current cache TTLs in Anthropic docs before writing numbers (T3 states 5 min API, 1 h subscription in a code comment; I did not check Anthropic's page).
2. **Capped, delta-only hand-offs that name what was cut.** Change: in repair rounds a carried reviewer or a repaired maker receives only what changed since it last saw the work (the repair diff plus its own previous verdict), under a fixed size cap, with a line listing omitted items. This is the context-side half of design section B. Cost: low to medium (change the brief and hand-back templates in `orchestration/references/briefs-and-handoffs.md`; no tool needed).
3. **Measure re-read cost from transcripts, split cache read from cache creation.** Change: the usage report reads the session transcript files per agent run and reports uncached input, cache read, cache creation and output, with a `hasSubagents` style flag, so each job's "evidence.md" shows which stage causes the re-read. Cost: low if J022's report already reads transcripts; otherwise medium (a reader script). Gives the data to tune Session size.
4. **Review the repair's diff, and checkpoint the rough.** Change: a git ref (not a commit) taken when the owner approves a rough; reviewers in rounds 1+ get the diff since the previous round. Helps "roughs rebuilt as finals" by making the delta between rough and final explicit. Cost: low (a small tool in `tools/`, a line in the recipes). Benefit is weaker than 1-3 and partly [inf].
5. **Non-blocking delegation with wake-on-completion.** Change: where the lead waits on one maker while others could run, start them in the background and act on each completion as it arrives, instead of one batch call that waits for the slowest. Cost: medium; depends on what Claude Code 2.1.306 supports for background agents (not checked here). Treat as an idea to test in the Claude Code docs, not a T3 feature to copy.

## 4. What does not apply to us

- **Multi-provider layer** (Codex, Cursor, Grok, OpenCode, Antigravity adapters, ACP registry, provider switch service): we run only Claude Code. No gain.
- **Mobile, web and Electron clients, remote access, relay, background service:** a UI and hosting layer. The service is not supported on Windows (docs/user/background-service.md [doc]) and we work in the Claude Code desktop app.
- **Event-sourced database, projections, replay-safe schemas:** engineering for a multi-client server. Our state is markdown files by design.
- **PR creation, stacks, auto-merge, GitHub/GitLab/Azure:** our deliverables are Roblox assets and game code gated by `tools/verify.py` and owner gates.
- **Permission modes and approval prompts:** not a speed problem for us; owner gates stay.
- **No answer to our biggest cause:** the 48-run cutscene job and the 5-7 reviewers come from our job recipes. T3 has no role chain, review chain or job size model, so it offers nothing on cutting agent count; that stays with J023 design sections B to F.
- **Sync of the harness settings:** T3 settings live in its own UI; for us the owner applies Claude Code settings (claude.md, Settings row).
