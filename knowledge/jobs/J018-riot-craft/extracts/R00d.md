## Findings

### R00d-F01 UX first, then UI, then motion feedback
- principle: UX defines where every piece of information lives and the player's path to it with the fewest actions; UI then builds the visuals on that map; motion graphics reinforce the message and give feedback on each interaction. The two must work closely; one person can hold both.
- why: A beautiful screen on a bad path still costs the player extra steps; visuals can only make a good flow more intuitive (R00d:4595-4599).
- apply: For every screen, the ui-ux-designer first writes the flow (entry point, decision, steps to reach each item, exit) and counts taps before any Figma styling. Default [inference]: any frequent action (equip, buy, claim) reachable in 2 taps or fewer from the HUD. Then style in Figma, then specify motion and feedback (tween, sound cue) per interaction.
- check: Walk the flow in a Studio play-test capture and count taps per task against the flow sheet; any extra tap must have a reason.
- mistake: Styling screens before the flow exists. [inference]
- example: Workflow summary: UX maps information flow, UI builds shape, colour, layout, values consistently, MoGraph reinforces messaging and gives feedback (R00d:4958-4983).
- roblox_fit: Phone players tap with thumbs on small screens, so each extra tap and each small target costs more than on PC. Touch is the default input on touch devices (`knowledge/external/roblox-creator-docs/input/index.md:27`).
- roles: ui-ux-designer, game-designer, feature-builder, orchestrator, sound-designer
- topic: ui-ux (secondary: pipeline-tech)
- lines: R00d:4559-4605, R00d:4958-4983

### R00d-F02 Visual design: complex information made simple to act on
- principle: At its core, visual design presents complex information in a simple way that the audience can understand intuitively and act on.
- why: Players decide in moments; anything they must decode delays the action.
- apply: For every UI element, icon, thumbnail or HUD meter, write the one thing the player must understand and the action it leads to; remove what does not serve it.
- check: Show the capture at player size (thumb_check.py for icons) and state in one sentence what the player learns and does; if two reviewers say different things, simplify.
- mistake: Decoration that adds information the player cannot use. [inference]
- example: Logos, typography, packaging, web and game UI all share this core (R00d:4613-4629).
- roblox_fit: Phone screens hold less, so the simplification must be stronger than on PC. [inference]
- roles: ui-ux-designer, art-director, marketing, game-designer, vfx-designer
- topic: ui-ux (secondary: visual-hierarchy)
- lines: R00d:4609-4629

### R00d-F03 Design for the audience and the device
- principle: Know who the audience is, how they think, what they connect with, where and how they see the UI, and what information they need and when. Playing on PC is very different from playing the same game on mobile or console, and the UI changes with it.
- why: Layout, target size and information density that work with a mouse fail under a thumb on a small screen.
- apply: Each screen brief names the target devices (for Roblox: phone first) and the moment the player needs each item. Make separate Figma frames for phone and PC/console where the layout must change, not only a scaled copy. Use ScreenInsets safe areas and adapt to the preferred input.
- check: Capture the screen in Studio device emulation at a phone size and a PC size; check that every needed item is visible, reachable by thumb and not under the top bar or a notch.
- mistake: One PC layout scaled down for phones. [inference]
- example: Fortnite PC versus mobile interface (R00d:4659-4665).
- roblox_fit: `ScreenGui.ScreenInsets` keeps UI in the safe area clear of the top bar and cutouts (`knowledge/external/roblox-creator-docs/_includes/ui/screen-insets.md:9-13`); `UserInputService.PreferredInput` adapts to touch, gamepad or keyboard (`knowledge/external/roblox-creator-docs/input/index.md:27-31`); mobile input page `knowledge/external/roblox-creator-docs/input/mobile.md`.
- roles: ui-ux-designer, feature-builder, qa-lead, game-designer, marketing
- topic: ui-ux (secondary: world-level-readability)
- lines: R00d:4631-4665

### R00d-F04 The genre sets the amount of UI
- principle: Information-heavy genres need robust UI that keeps a lot of information easy to reach; narrative games may need very little real-time UI.
- why: The UI load must match how much live information the player needs to make decisions.
- apply: In preproduction, the game-designer lists the information the player needs per moment; the ui-ux-designer sizes the HUD from that list. Card, tycoon and simulator games plan for many screens; obby or story games keep the HUD minimal.
- check: Count HUD elements visible during core play and map each to a listed player need; remove any with no need.
- mistake: not stated
- example: A trading card game is "90% UI"; 4X and simulation games need a lot; narrative games minimal (R00d:4674-4691).
- roblox_fit: Small phone screens make extra HUD elements cover the play view; keep the HUD as small as the genre allows. [inference]
- roles: ui-ux-designer, game-designer, art-director
- topic: ui-ux (secondary: game-design-fun)
- lines: R00d:4666-4691

### R00d-F05 UI is every screen, not only the HUD
- principle: UI covers level maps, character select, inventory, level editors, skill trees, lore and web pages, quest windows and more, not only the overlay on gameplay.
- why: Each screen the player sees is part of the same experience; forgotten screens get built ad hoc and break consistency.
- apply: At job start, list every screen and popup the feature needs (including empty, error and reward states) before designing any one of them.
- check: Compare the screen list to the feature flow; any screen reached in play-test but missing from the list is a finding.
- mistake: Designing only the HUD and improvising the rest. [inference]
- example: Maps, select screens, inventories, editors, skill trees, quest windows (R00d:4693-4709).
- roblox_fit: Roblox also has in-world UI (BillboardGui, SurfaceGui), which belongs to the same list (`knowledge/external/roblox-creator-docs/ui/in-experience-containers.md:18,95`).
- roles: ui-ux-designer, game-designer, orchestrator, feature-builder
- topic: ui-ux
- lines: R00d:4693-4709

### R00d-F06 One UI ecosystem with rules for meaning
- principle: The UI designer creates an ecosystem for the whole game: every part should feel unified and share one high-level flow, with rules for what each colour, text style and screen position means. Everything affects everything else.
- why: Consistent meaning lets the player learn a code once and read it everywhere; an inconsistent colour or position sends a false signal.
- apply: Write a UI rule sheet in the art bible: colour roles (e.g. currency, danger, rarity, confirm/cancel), text styles per level, fixed screen zones per information type. In Figma use shared components; in Roblox use style tokens. VFX and in-world markers reuse the same colour roles.
- check: Sample colours of every button and label in captures and compare to the role table; any colour used for two meanings, or one meaning shown in two colours, fails.
- mistake: Each screen chooses its own colours and positions. [inference]
- example: "There needs to be rules for the meaning behind different colors, text, position on screen" (R00d:4729-4735).
- roblox_fit: Roblox UI styling supports tokens and themes as global variables (`knowledge/external/roblox-creator-docs/ui/styling/index.md:11-19`).
- roles: ui-ux-designer, art-director, vfx-designer, feature-builder, reviewer, environment-designer
- topic: style-identity (secondary: ui-ux, light-colour)
- lines: R00d:4711-4737, R00d:4969-4973

### R00d-F07 Core thematic first, then explicit style rules
- principle: Begin a UI (re)design by defining the core thematic, then set specific rules for typography, iconography, colour, shape language and animation; every visual decision serves the thematic.
- why: A thematic gives one test for every choice and makes the UI feel like the game's world.
- apply: The art-director states the UI thematic in one line in the art bible (e.g. a material or world motif); reference-images makes UI mood frames from it; the ui-ux-designer derives the five rule groups (type, icons, colour, shape, motion) and the Figma style book from those anchors.
- check: For each new UI piece, name which thematic rule it follows; review side by side with the anchor UI frame at player size.
- mistake: Generic UI that could belong to any game. [inference]
- example: League client update built around "hextech magic" as core thematic (R00d:4743-4777).
- roblox_fit: Kit UI style skills (cartoon, anime, pixel, stud) are style books of this kind; the thematic chooses among them. [inference]
- roles: ui-ux-designer, art-director, reference-images, marketing, vfx-designer
- topic: style-identity (secondary: ui-ux, shape-silhouette)
- lines: R00d:4739-4777

### R00d-F08 Proximity creates meaning
- principle: The brain associates elements by proximity; what is placed next to what tells the player how they relate.
- why: A bar next to an enemy name reads as that enemy's health; an XP counter next to a bar reads as progress to the next level.
- apply: Place every value next to the thing it describes (health over the unit, cost on the buy button, timer on the objective). Keep unrelated elements apart with clear spacing.
- check: In a capture, cover the labels and ask what each bar or number belongs to; if the nearest object is the wrong one, move it.
- mistake: Putting a value near the wrong object, which creates a false association. [inference]
- example: Bar next to enemy name = enemy health bar; XP counter next to bar = "far from level 6" (R00d:4803-4813).
- roblox_fit: For world units, a BillboardGui keeps the bar attached to its unit (`knowledge/external/roblox-creator-docs/ui/in-experience-containers.md:95`); with many players and effects on screen, keep these short and close.
- roles: ui-ux-designer, vfx-designer, game-designer, feature-builder, level-design
- topic: visual-hierarchy (secondary: ui-ux, composition-focus)
- lines: R00d:4792-4813

### R00d-F09 Layout controls reading speed
- principle: Layout affects how quickly the viewer finds information, and games often need critical information very fast.
- why: In action, the player only glances at the UI; anything not found in that glance is missed.
- apply: Rank HUD information by urgency; put the most critical items in fixed, prominent positions near the play focus, less urgent items at the edges or in menus. Default [inference]: critical state (health, ability ready, objective) readable in under 1 second.
- check: Show a phone-size capture for about 1 second and ask what the health, ability state and objective are; failure = layout change.
- mistake: Critical information buried among secondary information. [inference]
- example: Live esports cast as the fast-reading case (R00d:4814-4823).
- roblox_fit: Thumbs cover the bottom corners on phones; critical info must not sit under the touch controls. [inference]
- roles: ui-ux-designer, game-designer, qa-lead
- topic: visual-hierarchy (secondary: ui-ux)
- lines: R00d:4814-4821

### R00d-F10 Familiar first, creative second
- principle: There is no single right layout; balance familiarity and intuitiveness with creative arrangement.
- why: Familiar placement uses habits the player already has; creativity gives identity.
- apply: Keep genre conventions for core controls (e.g. Roblox players expect common positions for shop, inventory and jump); spend creativity on style and secondary screens.
- check: Compare layout to two or three successful games in the genre; any departure for a core control needs a reason.
- mistake: not stated
- example: Layout as an open-ended puzzle (R00d:4833-4839).
- roblox_fit: Roblox core UI already occupies the top bar; game UI must work around it (`knowledge/external/roblox-creator-docs/_includes/ui/screen-insets.md:9-13`).
- roles: ui-ux-designer, art-director
- topic: ui-ux
- lines: R00d:4787-4791, R00d:4833-4839

### R00d-F11 Understood versus felt
- principle: Visual design aims for the message to be clearly understood; motion aims for it to be clearly felt.
- why: Movement adds weight and emotion to a state change (a reward, an error, a level up).
- apply: For each UI event, specify both: the static state that tells (label, icon, colour) and the motion plus sound that makes it felt (scale pop, shake, glow).
- check: Mute and freeze: the static frame must still explain the event; then play it: the motion must match the intended feeling.
- mistake: not stated
- example: UI is "always moving, and changing, and updating" (R00d:4840-4861).
- roblox_fit: UI motion uses TweenService on position, size, rotation, transparency, colour and stroke (`knowledge/external/roblox-creator-docs/ui/animation.md:19-251`).
- roles: ui-ux-designer, vfx-designer, animator, sound-designer
- topic: ui-ux (secondary: vfx-reads-timing)
- lines: R00d:4840-4861

### R00d-F12 You cannot polish a bad design into working
- principle: Polish and flair matter, but you cannot polish a bad design into working. Functionality and experience come first; the art and motion should always complement the information delivered.
- why: Effects on a confusing screen add noise, not clarity.
- apply: Review flow and layout in greybox (Figma wireframe or plain Studio frames) and pass them before adding gradients, glows or tweens.
- check: The wireframe pass must work on its own in a play-test; then each added effect must name the information it supports.
- mistake: Treating motion as polish that will fix a weak layout.
- example: "you can't polish a bad design into functioning the way you want" (R00d:4867-4871).
- roblox_fit: Every extra animated element costs performance on phones. [unverified]
- roles: ui-ux-designer, vfx-designer, art-director, reviewer, game-designer
- topic: ui-ux (secondary: critique-feedback)

### R00d-F13 Motion goal: responsiveness
- principle: Interactions are fast; clicking feels fluid and effortless.
- why: Delay between tap and response makes the UI feel broken or laggy.
- apply: Every button gives immediate feedback (press state, sound) on input, before any server answer. Default [inference]: press feedback within the same frame; UI open/close tweens about 0.1-0.25 s.
- check: Frame-by-frame capture at 30 fps from the tap: feedback visible on the next 1-2 frames; count tween frames.
- mistake: Long transitions that block input. [inference]
- example: Listed as goal one of five (R00d:4893-4901).
- roblox_fit: Show client-side feedback at once, and keep the server authority for the result. [inference]
- roles: ui-ux-designer, feature-builder, sound-designer, qa-lead
- topic: ui-ux (secondary: weight-timing)
- lines: R00d:4893-4901

### R00d-F14 Motion goal: intention
- principle: Motion leads focus toward key actions and pathways when needed.
- why: Movement draws the eye first; use it to point, not to decorate.
- apply: Animate only the element the player should act on now (e.g. pulse the claim button, slide in the next step); keep others still.
- check: In a capture with motion, the moving element must be the intended next action; count animated elements per screen (default [inference]: one attention motion at a time).
- mistake: Everything moving at once, so nothing leads. [inference]
- example: Goal two (R00d:4903-4907).
- roblox_fit: not stated
- roles: ui-ux-designer, vfx-designer, game-designer
- topic: ui-ux (secondary: composition-focus)
- lines: R00d:4903-4907

### R00d-F15 Motion goal: awareness
- principle: Elements respond adaptively from their location: they appear from or return to where they relate.
- why: Motion that starts at the source shows the player where something came from and where it went.
- apply: Popups grow from the button that opened them; rewards fly to the counter they increase. Specify the start and end anchor per tween.
- check: Frame captures: first frame starts at the source element, last frame at the destination.
- mistake: not stated
- example: Goal three (R00d:4909-4913).
- roblox_fit: Use AnchorPoint and positions to set the start point. [unverified]
- roles: ui-ux-designer, feature-builder, vfx-designer
- topic: ui-ux
- lines: R00d:4909-4913

### R00d-F16 Motion goal: consistency
- principle: Element types and actions use repeated motion patterns to establish familiar behaviours.
- why: The player learns the motion meaning once ("this slides in = notification").
- apply: Define a short motion table per element type (button press, popup open, toast, reward) with easing and duration; all screens reuse it.
- check: Compare tween parameters across screens in code or data; differences for the same element type fail.
- mistake: Each screen inventing its own transitions. [inference]
- example: Goal four (R00d:4915-4921).
- roblox_fit: Easing style is set per tween (default Quad) (`knowledge/external/roblox-creator-docs/ui/animation.md:406-412`); keep it in shared data, not per script.
- roles: ui-ux-designer, feature-builder, reviewer, vfx-designer
- topic: ui-ux (secondary: style-identity)
- lines: R00d:4915-4921

### R00d-F17 Motion goal: physical intuition and brand
- principle: UI elements are stylized to fit the game's brand and feel natural; their movement is affected by forces such as friction and scale. The motion style carries a feeling.
- why: Movement that obeys a material (paper, metal) or scale (huge, sweeping) tells the player the tone before they read anything.
- apply: Choose one motion "material" per game or event in the art bible (light paper flutter, heavy metal slam, grand parallax) and apply it to UI, login and title screens. Parallax layers for big moments.
- check: Watch the transition and name the material it suggests; it must match the art bible line.
- mistake: Generic linear tweens that fit no brand. [inference]
- example: Enter the Gungeon's Ammonomicon opened by a bullet; Rift Rivals login moves like paper; World Championships login uses sweeping parallax for grandeur (R00d:4929-4949).
- roblox_fit: Easing styles (Back, Elastic, Bounce) give material feel (`knowledge/external/roblox-creator-docs/ui/animation.md:406-474`).
- roles: ui-ux-designer, animator, vfx-designer, marketing, film-director, art-director
- topic: style-identity (secondary: ui-ux, weight-timing)
- lines: R00d:4923-4949

### R00d-F18 Start from player pain points

- check: Each proposed UI change names the pain point it fixes and where it was observed.
- mistake: not stated

### R00d-F19 Learn by recreating loved work, then twist
- principle: Copying work you love teaches techniques faster than a blank canvas; the designer recreated favourite games' HUDs and menus, then added their own twist.
- why: Recreating forces you to understand why the reference works.
- apply: Before designing a new UI or motion style, collect 2-3 successful references in the genre, make a quick recreation or paint-over study of their structure, then change it toward our thematic. References are study, never final assets.
- check: The final design must differ visibly from the references in style while keeping the learned structure.
- mistake: Starting from nothing; or stopping at the copy. [inference]
- example: Recreating HUDs and menus of favourite games (R00d:5043-5045).
- roblox_fit: Copying assets or branding of others is not allowed; copy structure only. [inference]
- roles: ui-ux-designer, reference-images, art-director, animator

### R00d-F20 Try many, keep the right mistakes

### R00d-F21 A game has four components
- principle: A game has a goal (objective), opposition (something to overcome), decisions (ways to get past the opposition) and rules (the framework that governs it all).
- why: Removing any of the four removes the game; eating cereal is not a game until rules and opposition are added.
- apply: Each loop or mini-game spec states all four in one line each; an obby section, a boss or a minigame without real decisions is flagged.
- check: Review the spec: can each of the four be named? If "decisions" is empty, it is an activity, not a game.
- mistake: Activities with no opposition or no decision. [inference]
- example: Tennis is a game; eating cereal is not (R00d:5195-5205).

### R00d-F22 Name the type of fun
- principle: "Fun" is not a useful concept; set a specific target experience instead, such as an alternate fantasy, thrill or sensation, fellowship, mastery of a challenge, exploring the unknown, or creativity and expression.

- apply: The game profile and every feature brief name one or two target types of fun from this list; art, sound, VFX and UI briefs quote it.
- check: Each brief and review states which fun type it serves; work that serves another fun type is flagged.
- mistake: Briefs that say "make it fun".

### R00d-F25 Mechanics alone set the tone
- principle: Mechanics (rules and interactions) strongly shape a game's thematic feel even without art; behaviour defines what a thing is and how the player feels about it.
- why: Players read objects by what they do: a cube that damages an area around itself and then disappears is a bomb; a larger damage area increases the feeling of danger and power.
- apply: When designing an ability or object, write its behaviour first and check that it already implies the theme; VFX and sound then support that behaviour (area size, duration). Tuning numbers (radius, damage) are tone tools, not only balance.
- check: Greybox test: with placeholder parts only, ask a tester what the object is; the answer should match the intended theme.
- mistake: not stated
- example: Innocent cube on a grid turned into a scary explosive through mechanics (R00d:5337-5363).

### R00d-F26 Movement patterns give character

### R00d-F27 Art and mechanics must imply the same thing
- principle: Artists and designers together make sure mechanics imply the right theme and vice versa; when art and mechanics disagree, play feels unnatural.
- why: Players predict behaviour from appearance; a broken prediction feels wrong and unfair.
- apply: Any object that looks soft, open or weak must behave that way, or be redrawn: blocking objects look solid, walkable gaps are walkable, cover looks like cover. Character roles (tank, assassin) must match their visual design.
- check: In play-test, list every place where appearance and behaviour disagree (collision on a doorway, bullets stopped by leaves).
- mistake: "open doorways that you can't walk through" (R00d:5413-5415).
- example: Bushes that stop bullets, mailboxes that stop a speeding truck; original Shen was a tank to designers and a stealth assassin to artists (R00d:5407-5423).

### R00d-F28 Make progress toward the goal visible
- principle: Make it clear to players how they progress toward the goal; without that they cannot know if they are doing well. Progress markers also tell the opposing side when to push.

### R00d-F30 Opposition plus tools; the right frustration
- principle: Opposition is often what makes a game fun but can make it frustrating; some frustration is fine if it is the right kind. The designer provides both the opposition and the tools to overcome it, working for and against the player at once.
- why: Challenge creates the satisfaction of winning.
- apply: For each obstacle, spec name the counter tool or skill the player has; tune difficulty so the counter is learnable.
- check: For each obstacle in the spec, a counter is listed; play-test failures should be attributed by testers to their own mistakes.
- mistake: Removing all challenge to avoid frustration. [inference]
- example: Ninja Gaiden boss "Bloody Malth" lost to repeatedly, finally beaten at the last second (R00d:5573-5615).

### R00d-F31 Fairness: clear expectations and consistency
- principle: Clear expectations and consistent design make a game feel fair; fairness is separate from difficulty. Inconsistent or unpredictable behaviour feels unfair because the player cannot learn from failure.
- why: Learnable failure keeps players trying; random-feeling failure makes them quit.
- apply: Every threat telegraphs before it hits (animation anticipation, VFX warning, sound cue) and behaves the same each time; no hidden traps right after an obstacle.
- check: Play-test: after a failure, can the tester say what killed them and what to do differently? Check that the same attack always has the same tell.
- mistake: "Players overcome one obstacle only to be blindsided by the next" (R00d:5656-5658).
- example: Troll Mario Maker levels: funny to watch, bad for most games, novelty wears off (R00d:5652-5666).
- roblox_fit: Telegraphs must read on a phone at the game camera. [inference]
- roles: game-designer, level-design, qa-lead, vfx-designer, animator, sound-designer

### R00d-F32 Mix luck and skill on purpose
- principle: Luck and skill shape opposition. Pure luck suits games not meant to need skill; competitive games leave little to chance. A mix can give a random start with skill-driven moment-to-moment play, so skilled players can come back and less skilled players can still have exciting games or win.
- why: Luck keeps outcomes open for everyone; skill makes wins feel earned.
- apply: Decide where randomness sits in the loop (start, loot, drops) and where skill decides; document the ratio per mode for the target audience.
- check: Simulate or play-test: can a skilled player recover from a bad random start? Can a new player sometimes win?
- mistake: not stated

### R00d-F35 Separate goals from tactics
