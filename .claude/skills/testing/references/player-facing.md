# Player-facing rows: conditions, the row catalogue, hooks, borrowed measures

The crafts judge how a thing looks, sounds and feels. I prove that what players see and hear tells the truth about what the game decided, and that it still does so under the conditions players really play in. Each row below becomes one or more trace-table rows (`SKILL.md` §3 step 2) with its oracle, conditions and input.

## 3. Sources of truth and test hooks (ask at plan time)
**Sources I collect** (step 1), each with its revision: the architect's presentation contract (its rows and check seeds go straight into my trace table: `architecture/references/presentation-contract.md` §2, §6) and the builder's feedback stack sheet (`engineering-craft/references/presentation.md` §1); the game designer's feedback stack (attempt cue and outcome rows per action), hazard rule table and outcome tiers; the UI state list, copy table and motion table; the animator's timing list (event names, seconds, source frame, frame rate); the VFX read card (truth values with their data fields, rate, burst, merge window, caps, reduced variant, per-viewer lines); the sound event list (trigger, cue id, event id, priority); the progression designer's odds and display fixtures; the comfort settings in the feature spec. A row whose truth has no sheet goes back to the briefer as a question.

**Hooks I ask the builder for**, as a ticket against the architect's plan or the feature contract, before the build. The builder's hook set is `engineering-craft/references/presentation.md` §9 (attributes on a `TestHooks` folder, Studio only, because an MCP `require` reaches a separate module copy); I ask by those names:
| Hook (attribute) | Serves | Note |
| --- | --- | --- |
| `Reject` = reason code | PF-02, PF-11 | the server denies the next requests with that reason |
| `DelayMs` = number | PF-02 pending path | the server waits before answering |
| `Trigger` = event id; `Rate` = `<event id>:<per second>:<seconds>` (logs the live-copy count) | PF-03, PF-08, PF-10, PF-14, PF-16 | 100 at 1 per second; a burst of about 20 per second |
| `DebugShape` = true | PF-04 | built from the same data row as the effect, never a second constant |

## 4. Measures borrowed from partner books (screening aids)
I point to the owner's recipe and never copy it. Frame folders: no kit tool records one yet; ask the lead for the capture route at plan time (the same request as the VFX designer's, `vfx-craft/references/measure.md` §1); without one, the F lines are "not verified" and the row rests on the log and stills. Every image measure is a screening aid: a FAIL or a borderline reading (within about 10 % of its threshold) is checked by eye on the stills it names before the finding goes out, and a pass on a case from its "misses" list stands only after that eye check. Log and data oracles (server values, data diffs, logged lines) are exact for what they record: a FAIL on a logged line or a server value stands without an eye check; a PASS that rests on the absence of a line (no outcome after a reject) also needs the still the row names, because a branch that does not log is invisible to the log.

## 5. What each input can prove
| Input | Can prove | Cannot prove (say so) |
| --- | --- | --- |
| Data, spec, config (D) | values, sizes, rates, odds totals, which axes are random, reduced variants listed | how anything reads or times on screen |
| Test results and the debug log (T) | rules, server results, event order and scheduling, counts, repeats | output timing on a device, the picture |
| One Studio still (C) | layout, presence, cover, contrast at that moment and condition | timing, onsets, sound, repetition, cost, other viewers, other quality levels |
| Frame folder at a known rate (F) | sequence, timing, identical windups and tells, flash count | sound, feel, device latency; a folder at an unknown rate gives frame counts only |
| Device capture with audio (Dev) | sync of sound and picture; muted read | server truth without an overlay; performance without a stats overlay |
| Owner at a playable preview (O) | feel at normal speed, whether a repeat tires | numbers |
A before/after pair shares the camera, seed, conditions and competing effects, or it is not verified. Slow playback finds problems but never proves feel. Every number names the device, viewport, quality level and frame rate it came from.
