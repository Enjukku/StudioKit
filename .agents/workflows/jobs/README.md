Kit folder: universal.

One saved Claude Code workflow per job type. `tools/sync_harness.py` copies each `job-<type>.js` byte for byte to `.claude/workflows/`, where `meta.name` becomes the slash command `/job-<type>`. Never edit the copies. Codex runs the same stages by hand from the `orchestration` skill's `references/job-types.md`.

## Contract every job workflow keeps
| Rule | Why |
| --- | --- |
| One stage per call: `direction`, `build`, `repair`. `stage: "proof"` returns `blocked` before any agent: "no proof stage (J024): direction → G1 → build → G3". An arg that switches a rule or a gate has no default: a missing or wrong one returns `blocked` before any agent starts, with the list of what is needed (`required`) | a workflow cannot pause for the owner (capability check C07); lead decision LD9 |
| What each stage runs. `direction`: D1 plan (the job lead: L 2-3 options with their image prompt rows, M one direction; the type's plan, revision 1); N1 in parallel (needs tables from the recipe's needs crafts, limits tables from its constraint owners; each reads only the plan and its brief); the merge (the job lead: `direction.md`, plan revision 2, the G1 packet rows, the conditional crafts as explicit hand-back fields); N2 and a second merge only on a conflict the job lead cannot settle. No sign-off step: each craft confirms the merged plan or names an incompatibility in its first build hand-back (`needs-decision`). `build` (same for L and M): production, one run per craft in the plan's dependency order; integration; the capture-and-scripts run; the review chain. `repair`: the affected makers with capped repair briefs, the capture-and-scripts run, the review chain | `orchestration/references/job-types.md` stage table; `rules/company.md` §4; J024 design §1-§4 |
| Needs step, in `direction` before G1: needs and limits tables (`templates/jobs/needs-table.md`: ≤ 12 rows, `omitted:` line) against plan revision 1; at most 2 rounds (N1; N2 only on a conflict, only the conflicting rows). Build reads the merged plan and never re-asks; a later need is a contract change. No rough, proxy, board, animatic or check-in step runs; a craft builds its real part once | `rules/company.md` §4 step 2, step 7; owner J023-D2, D6, D7; J024 design §2-§3 |
| Images: an image step writes its prompts first and generates only when its tools include Claude in Chrome and `imagesApproved` is true; otherwise it writes `image-prompts.md` next to its deliverable, returns `images: pending` and the stage result lists the batch in `images_pending`. Pending G1 pictures do not fail direction (the job lead's synthesis and the G1 packet use the prompt rows); a pending batch that later steps in the same call build on (the character reference set, UI icons and item art, kit model sheets, a marketing render) stops the stage as `blocked` there, so nothing is built or reviewed on unapproved images. The lead runs the batch with the owner between stages and passes the approved paths in `images`. Visual work never starts without an approved image path in its brief | lead decision LD2; `reference-images` §4; AGENTS.md §3.5 |
| No agent ids and no messages: sideways work goes through files in a fixed order (the producer writes, the consumer answers on that file, the owner of the contract merges). VFX writes each envelope first; sound answers on it | lead decisions LD1, LD3; owner goal "sound needs the VFX timing" |
| Review chain: the capture-and-scripts run first in every round (a scripts FAIL stops the other reviews until it is fixed); then the job lead's integrated review (always; sound sync from `cue_log`), the `reviewer` when the candidate changed code, the qa-lead for the player-facing logic the recipe names, the performance-engineer when `risks` names `performance`, the art-director with `newLook` (marketing: `launch`) or a non-empty `visual_flags`; risk-gated slots as the recipe says | `rules/company.md` §7; lead decision LD15; J024 design §4 |
| Repairs go to the makers in dependency order; a moved time makes VFX and sound recheck. After every repair round the candidate is re-imported, rebuilt and recaptured before the next review round | reviewers never judge stale captures |
| Selective recheck: round 0 runs the whole review chain. A later round runs the capture-and-scripts run, the qa-lead protected suite where the chain has one, the `reviewer` when a code-owning maker's files changed, every reviewer with a blocking finding in the previous round, and each reviewer whose area depends on a repaired layer (the job lead's integrated review after a visual or timing repair; the art-director after a visual repair, only when it is in the chain). Repair and recheck briefs are capped (own findings, changed parts with revisions, the protected list; ≤ 10 findings and about 1,500 words; an `omitted:` line; never another reviewer's full review file; `rules/messages.md` §6), built by the script and readable from `dump`. Each script states this dependency map in one table near its review chain. Every other reviewer keeps its verdict, listed in the stage result as `carried: <reviewer> (round n, revision r)` | `rules/company.md` §7; J023 design B |
| Capture and scripts: one `studio-operator` run (Sonnet) per review round imports or plays the frozen candidate, runs the gate and the type's measuring scripts, captures key frames and reads the Output-log cue times; its hand-back adds `visual_flags` and `cue_log`. The role that needs a probe names it in its hand-back; Opus roles never take routine captures | `rules/company.md` §7, §9 model row; J024 design §4.3, LD2 |
| Repair rounds: code findings 3, other findings 2, needs rounds 2 (N1, N2); then `needs-decision` | `rules/company.md` §9; lead decision LD5 |
| A role the workflow cannot route (a finding's maker or an affected role, or a reviewer-only role such as the live-ops reviewer) returns `needs-decision`; a dead agent (null) is `failed` and a step that returns any status other than `done` stops the stage with that status: never a pass | nobody drops work silently (`rules/company.md` §8) |
| Every `agent()` call sets `agentType` (the role), `model`, `effort` and the hand-back schema of `templates/jobs/handback.schema.json` (evidence before answers, `docs_read`, optional `lesson`); findings carry expected and observed | `rules/messages.md` §2-3, §6; lead decision LD11 |
| Every brief is built in the `rules/messages.md` §2 shape: `<intent>`, `<spec>` with packet line, `owner_words`, refs, inputs with revisions, owns, rules, `findings` for repairs, deliver, checks | quality: complete briefs |

| At most 5 agents at once; one Studio driver (`studioId` from the lead), one Blender user and one Claude in Chrome user at a time | `rules/company.md` §9 |

## Args per workflow
Every workflow takes `job` (the job folder id) and `stage`. "Stages" says where the arg is required; "opt" means optional with the default named.

| --- | --- | --- | --- |

| all | `gate` | opt | the owner's words at the last gate, verbatim (shown in `owner_words`) |
| all | `imagesApproved` | opt, `false` | the owner's yes for this stage's image batch, recorded in `decisions.md`; without it image steps return `pending` |
| all but marketing art | `studioId` | build, repair; also direction in character when `risks` names `new-enemy` (the behaviour test) | the one Studio instance this run writes to |

All: `event` (a job from a live-ops update brief: the live-ops-designer reviews the integrated candidate before G3 on the event capture set (marketing art: on the image files); its concept round fixed the premise, and the job still runs its own direction, build and review chain: J019-LD1); `performance` (the performance-engineer writes a limits table in `direction` and reviews in `build`, J024). A stage result carries `status`, `outcome`, `steps`, `images_pending` (batches for the lead), `skipped_slots` (one line per risk-gated slot this run skipped because `risks` does not name its risk; the lead copies them into the job card), `lessons` (every agent's lesson draft, for the lead to file in `knowledge/inbox/`), the `carried: <reviewer> (round n, revision r)` line of every verdict a later review round kept, the conditional crafts the merge switched on, and the stage's own fields (`g1`, `beat_sheet`, `blocking`, `new_requests`, `required` when blocked).

## Smoke run (mechanics only)
`args.smoke: true` puts every agent on Haiku at low effort with a note: no Studio, Blender or browser, no files, placeholder hand-backs, no lessons collected. It tests the real Workflow runtime, never quality; the lead files nothing from it. Call the workflow by `scriptPath` after an edit in the same session (capability check C25).

## Test
`python -m unittest tools.tests.test_job_workflows` runs every script here under `tools/workflows/wf_harness.mjs` with fake agents (no tokens). The harness fails a run on: an `agent()` call without role, model, effort or schema; a schema that differs from the hand-back template; a role file missing or a model off its tier; a phase not in `meta.phases`; more than 5 agents at once; two agents holding the Studio, Blender or the browser at once; a brief that names peer messages. The tests check: bad and missing args are refused before any agent, and `stage: "proof"` is refused (J024); every stage ends `done`; repair rounds are bounded and repair briefs keep the cap (read from `dump`); a later review round reruns only the reviewers the selective recheck names and lists the others as carried; each type's minimum run count with clean fakes (`J024-flow-cuts-r2/design.md` §6); each conditional craft has an on and an off test; a dead agent is never a pass; pending images are listed; the capture-and-scripts run comes first every round; VFX runs before sound; the cutscene stops for a new cast in direction; code review runs wherever code is in the candidate. One file per type, `tools/tests/test_job_workflow_<type>.py` (J019), checks that type's recipe rows: `risks` missing, not a list or with an unknown token is refused before any agent; each risk-gated slot runs only with its token and a skipped slot is a line in the result; the `event` live-ops review runs after the creative order, before G3, on its capture set, and its findings go to makers inside the round limits; consumers answer before producers build (needs tables before G1; markers before VFX and sound; the floor-material list before materials); G1 results carry failed options and closed doors, and every gate result the could-not-check list and owner-confirmed lines. It is part of the gate (skipped where Node.js is not installed).

## Running one (the lead)
Only after the owner has asked for the job and answered the previous gate. Example: `Workflow({name: "job-cutscene", args: {job: "J021-boss-intro", stage: "build", size: "L", newLook: false, risks: [], studioId: "<id>", images: ["content/art/refs/<approved>.png"], gate: "<owner's G1 words>"}})`. A resumed run returns the cached result of every step whose brief did not change: resume after new args (for example `images` after a pending batch), but rerun fresh when only a file the agents read changed (for example a measured slot size). Before the gate pause, write the stage state to the job files (`rules/assistants/claude.md`, Gate pause). Report the agent count and usage at the next gate; file every entry of the result's `lessons` in `knowledge/inbox/`.
