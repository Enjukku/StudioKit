# Animation craft: build, export and play it

## 1. When this skill starts
After `animation-design` produced the read, the technique per part, the set, the beat sheets, the picked key poses and the timing list draft. For a rigged asset the rigger has released the rig (`rig-pipeline` S5: rig sheet, control manifest, test record); you start at S6. For code-driven or physics motion you write a motion spec (§5) and stop there: a builder writes the code. Needs: Blender 5.x with the MCP add-on (or headless Blender), Roblox Studio for import and playback (`studio-mcp` skill), the game profile (camera, devices).

## 3. Steps (rigged asset: S6 → S7)
1. **Versions and inputs.** Record the Blender build, the FBX add-on check (`roblox_fbx.check_exporter() == []`), the rig sheet and control manifest revisions, the timing-list revision, the picked key poses and beat sheets. Work on a copy of the released rig file; never edit the rigger's file. *Check: build manifest in `content/anim/<asset-id>/`.*
2. **S6 rig acceptance.** Pose every §B extreme and stress pose through the control manifest only (key controls, never export bones: follow the manifest's keying policy). Also confirm the controls the read needs: shoulders and hips, the head's world-orient option (or a plan to counter-key it), hand or finger shapes, and every hook-shape part. Numbers first: `clip_check.py` `rom` on a sweep clip, contact holds, reset to rest. Images only for a failing number plus the hardest stress pose from the game camera. A fail → **one rig note** (`templates/rig/fix-note.md`) with every failed item; max 2 rounds. *Check: §H S6 row signed with evidence.*
3. **Clip setup** (`references/blender-keying.md` §2, §7). One named Action per clip with its slot assigned explicitly; frame range and effective fps (`render.fps / render.fps_base`) recorded; loop clips get the range policy of §4 C-09. Set up the **game camera** once per asset (the game profile's angle, distance and field of view, a phone-size render, a player-sized reference and a capture of the game's ground behind) and the black-fill render settings. Keep clip ids, event times, contacts and loop policy in data (the animation set and timing list), not in display names. *Check: Action list matches the animation set; game camera recorded in `renders/cameras.json`.*
4. **Blocking pass.** Pass 1: the root (or hips) and feet only, whole body keyed on shared frames so timing stays movable; render a root-only preview at the game camera. Pass 2: the picked key poses on the same frames, gaze and head direction included; holds as copied key pairs (CONSTANT interpolation only for a quick pose review). Expect it to look rough for a long time. Run the blocking lines (`review.md` §8a); then the **check-in**: show the blocking preview and the key-pose black-fills to the brief's reviewer (the film-director for cutscenes, the proof reviewer for a character proof, VFX and sound for an effect's beats) and send the draft timing list, before any spline. When the brief names no check-in reviewer, the check-in is your §8a record plus the black-fills and the root-only preview, written to the job folder before splines; say so in the hand-back. *Check: §8a lines PASS or explained; the check-in recorded; key poses and beat frames frozen from here unless a new decision moves them.*
5. **Breakdowns and offsets.** Breakdowns placed on purpose where the body would otherwise blend through itself; weight shifts before lifts; the driver leads and the rest follows; feet stay down for a push-off; counter-limbs on fast moves; offsets break shared keys apart so actions start at different times and paired limbs do not twin. Offsets move a key with both handles. *Check: the §8b weight and timing lines (S-01 to S-14) on the samples.*
6. **Spline.** Interpolation per channel and segment (`references/blender-keying.md` §3); shape eases with handle types and handles, not extra keys; read the sampled curves for flips, spikes and plateaus and fix rotation flips at the source; keep arcs and spacing. Run `clip_check.py` after the pass (`python tools/anim/clip_check.py samples.json --timing timing.json --manifest control-manifest.json --tol tol.json --up z`; tolerances come from the rig sheet, game profile or owner, else results are MEASURED). *Check: no FAIL in the clip_check report, or a reason per item; S-18 clean.*
7. **Polish.** One named problem per pass: render, find what feels worst, fix it, look again. Overshoots and settles, hands and fingers, then secondary chains (a mass first, then offsets), then eyes and face last. A section that keeps breaking is cleared and re-keyed, not patched. Stop at the brief's stop criteria. *Check: §8b complete; pass log with one problem per pass.*
8. **Bake and export** (`references/blender-keying.md` §5). Bake the export skeleton with visual keying on a copy, then `roblox_fbx.export(path, kind="clip")` per clip (or one multi-clip file when the import route is the Clip Editor). In-place locomotion by default: native root motion is not released (RA41, RR39-RR41). *Check: the export log lists the intended clips, range and fps only.*
9. **Round trip.** Re-import the FBX into a fresh scene, sample it and compare with the source samples (clip_check on both; poses, length and contacts match). *Check: `tests/roundtrip-<clip>.json`.*
10. **Roblox import and publish** (`references/roblox-playback.md` §1). Import route named (Animation Editor import / Clip Editor / Import 3D); the owner clicks Import or Publish when the brief says so (J005-D6: test place only). Set priority and loop on the asset; add markers from the timing list if they did not survive import (probe once per route, §4 C-17). *Check: the asset id and the route are in the animation set.*
11. **Play and judge in the game** (`references/roblox-playback.md` §2-4, §9-10). Server-created Animator and server playback when other players must see it; client Animator for cosmetic motion. Load once, cache the track. Read the Output log for marker times against the timing list. Capture stills at the game camera on the phone viewport in the real place, with effects on, then with effects hidden and in grayscale (MCP captures are stills, not video; sound sync needs a device capture). Run `review.md` §8c. *Check: MCP-verified rows in the check record; could-not-check list written.*
12. **Phone and scale** (`performance` skill; §6). The agreed scene with the peak on-screen count on the floor phone; without a phone the row is BLOCKED, never PASS. *Check: measured numbers or BLOCKED with reason.*
13. **Final timing list.** Times in seconds plus source frame and fps; mark which were confirmed in the Output log; the freeze frame and the sync rule written. Bump the revision and tell every consumer if a time moved. *Check: VFX and sound acknowledge the revision.*

Code-driven or physics motion: steps 1, then write the motion spec (§5), then review the builder's result in Studio against it (step 11 checks, Output-log event times).

## 4. Craft core: what separates working clips from broken ones
| ID | Practice | Evidence |
| --- | --- | --- |
| C-01 | Load with `Animator:LoadAnimation` (the Humanoid and AnimationController versions are deprecated); the Animator must be in Workspace first; each call makes a new track, so load once and cache, or fetch with `GetTrackByAnimationId` | [V] RA03-RA05 |
| C-02 | Replication: NPC and prop clips must be loaded and started on the server to replicate; a client-created Animator never replicates; a player's own client may start tracks on its Character's Animator. Cosmetic crowds and decoration use a client Animator on purpose | [V] RA02, RA42; TC10 |
| C-03 | Priority settles per joint, high to low: Action4, Action3, Action2, Action, Movement, Idle, Core; compare by name, never by enum number; default and catalog clips play at Core, so any custom clip at Idle or above overrides them joint by joint. A layered clip keys only the joints it drives | [V] RA09-RA10 |
| C-04 | Priority first, weight second; same-priority tracks blend by weight. Defaults: fadeTime 0.1 s for Play, AdjustWeight and Stop; weight 1; speed 1. Fade lengths are a design or measured value, written in the set | [V] RA12-RA14 |
| C-05 | After `Stop()`, call `Play()` before adjusting that track. Use `Ended`, not `Stopped`, to know its influence is gone. Avoid `Stop(0)` on Motor6Ds with MaxVelocity 0 | [V] RA14-RA15 |
| C-06 | Speed: negative plays backward, 0 pauses; real duration = Length / Speed; Length is 0 until loaded; TimePosition is settable only while playing | [V] RA16-RA17 |
| C-07 | Markers: read with `GetMarkerReachedSignal(name)`, connected before `Play()`; payload in the Parameter string. `KeyframeReached` is deprecated; `GetKeyframeMarkerReached` (named in one doc page) does not exist. Marker behaviour under throttling or low frame rate is undocumented: markers drive cosmetics only | [V] RA19-RA22 |
| C-08 | Gameplay never waits on a marker or a client's visual state: the server owns hits, damage, open, occupied | [V] TC30 |
| C-09 | Loops: a Roblox loop does not blend from the last key to the first, so the last key repeats the first pose and the clip length equals the period. Check pose and velocity at the seam after import | [V] RA18 |
| C-10 | Blender keying through the current API: Actions with slots and channelbags (`action.fcurves` was removed in 5.0); `fcurves.ensure(..., group_name=)` needs 5.0+; batch keys with `keyframe_points.add` + `foreach_set('co', ...)` then `update()` | [V] RB30, RB39-RB40; KB rows |
| C-11 | Interpolation describes the span from a key to the next; set it and the handles on purpose (automatic handles can overshoot); one rotation mode per animated bone, the rig's | [V] RB42 |
| C-12 | FBX carries baked samples, never constraints, IK or drivers: bake the export skeleton with visual keying on a copy (the bake defaults are traps: `visual_keying=False`, `only_selected=True`, `clean_curves=False`) | [V] RB12, RB44 |
| C-13 | Never export with Blender's FBX defaults; use `tools/rig/roblox_fbx.py` (`kind="clip"`); start with simplification 0.0 so any later reduction has a baseline | [V] RB23 |
| C-14 | In-place locomotion; the controller owns travel. Avatar animations play in place: mute root translation before export | [V] RA41 |
| C-15 | Procedural layers on top of a clip write `Transform` in PreSimulation and skip when `Animator.EvaluationThrottled` is true; R15 avatar joints are AnimationConstraints when the avatar joint upgrade is on; Motor6D stays right for mechanical rigs | [V] RA24, RA28-RA30 |
| C-16 | IKControl needs Type, EndEffector, Target, ChainRoot; turn it off with `Enabled=false`, not weight 0 | [V] RA33 |
| C-17 | Whether Blender markers survive FBX import into Roblox markers is not documented: probe once per import route; the fallback is to add markers on the Animation Events bar from the timing list | [O] SD (not in the mirror, J006) |
| C-18 | A cap on playing tracks per character exists and warns; 64 is forum-reported, undocumented: never a budget. Leaked or duplicate tracks are the usual cause | [E] RA27 |
| C-19 | Cosmetic code motion runs on the client: a server-side tween replicates the property every frame | [V] RT1-05, TC01 |
| C-20 | Animation memory unloads only when scripts drop their references and connections; strip saved animation metadata from shipped rigs | [V] RA42-RA43 |
| C-21 | KeyframeSequence is what the editor saves; CurveAnimation is required for emotes and animation packs; converting quaternion curves cannot be undone | [V] RA31-RA32 |
| C-22 | No scale in clips: a KeyframeSequence pose stores only a CFrame, and CurveAnimation drives position and rotation per joint; squash and stretch take another route (a mesh swap or code-driven scale on a separate part, a VFX ring, dust or trail); bone scale on a skinned mesh is unverified: probe in Studio before relying on it | [V] `_api-reference/classes/Pose.yaml` (Pose.CFrame), `CurveAnimation.yaml` |
| C-23 | Our clips are baked one key per frame, so the Blender curves are what plays. Roblox interpolates between poses by PoseEasingStyle (Linear, Constant, Elastic, Cubic, Bounce, CubicV2) with no automatic arc: if a key reduction is ever applied, re-check arcs and spacing against the unreduced samples | [V] `_api-reference/enums/PoseEasingStyle.yaml`; KB16 |
| C-24 | Collarbone joints (LeftClavicle, RightClavicle) and finger joints (up to 15 per hand) exist only on advanced R15 rigs; a standard R15 body has 15 joints, so shoulder energy goes into the upper torso and upper arm, and hand shapes into bigger hand poses or a hand-mesh swap | [V] `characters/index.md` (advanced R15 joints) |
| C-25 | Hit-stop is a playback pause, not a clip edit: the builder calls `AdjustSpeed(0)` on the attacker's (and the animated target's) tracks and restores the speed after the stop; physics, debris and server results keep running. The clip supplies the freeze frame | [V] `_api-reference/classes/AnimationTrack.yaml` (AdjustSpeed: 0 pauses) |
| C-26 | Faces: dynamic heads take FaceControls channels (eyes closed, eye look, brows) in clips; a decal face cannot blink without a texture swap | [V] `_api-reference/classes/FaceControls.yaml`; CurveAnimation FACS folders |
| C-27 | Reduced motion is the player's setting (`GuiService.ReducedMotionEnabled`); builders read it. A clip's tell and contact must read without camera motion, shake or flashes; a reduced variant removes camera-driven motion, never the pose | [V] `_api-reference/classes/GuiService.yaml`; `production/publishing/accessibility.md` (reduced motion) |

## 5. Code-driven and physics motion: the spec (detail `references/motion-specs.md`; template `templates/anim/motion-spec.md`)
- You write what moves, the pivot or rail, travel, phases with lengths and curves (EasingStyle + direction, or a named custom curve), events, interruption rules, client or server, the reduced-motion behaviour, and the checks. A builder writes the code; values go into data.
- The same craft applies to props: a small anticipation (a latch rattle), eased spacing (no constant speed except for a mechanism at steady speed), a single clear arrival, a small overshoot and settle where energy should show (Back or Elastic easing), an end state that reads in a still.
- TweenInfo gives 11 easing styles, 3 directions, repeat, reverse and delay; a one-axis door or lever needs nothing more [V] TC03. A second tween on the same property cancels the first and Cancel leaves it mid-way: every spec states the end pose and the interrupt rule [V] TC02.
- Rigid props moved by code: anchor one root, weld the rest, move with `PivotTo` or CFrame [V] TC05; `BulkMoveTo` only for a measured bottleneck [V] TC06. For rigid hierarchies moved every frame, writing `Motor6D.Transform` in PreSimulation is the documented efficient path [V] TC07.
- Constraints: hinge servo (doors, gates), prismatic servo (lifts, sliding doors), motor (wheels, windmills) take few properties and sleep when idle; set a servo target once per state change, never per frame [V] TC12, TC14. Physics is simulated by the owner, so a free mechanism can look different per client: server-owned servo targets where everyone must see the same pose [V] TC13.
- A keyed multi-part mechanism (drawbridge with chains, windmill with gears) = Motor6D rig + AnimationController + Animator through `rig-pipeline`; a one-axis rigid door, lever or lift needs no rigger step [V] TC09.

## 6. Ambient loops at scale (detail `references/ambient-at-scale.md`)
- No documented per-copy cost exists for tween, Animator track, Motor6D, Bone or flipbook (SD01; a tween is quick to author, not proven cheaper per frame): measure the technique at the peak count on the floor phone before choosing it for hundreds of copies.
- One loop per system, never one Heartbeat or PreRender loop per object [V] TC08; a shared curve sampled with `TweenService:GetValue` avoids one Tween object per copy [V] TC04.
- Global wind moves terrain grass, clouds and particles only; flags, trees and signs need their own motion [V] TC19. Animated models get no SLIM or far LOD: plan the pop-in at the streaming radius [V] TC20. Client-set motion on server-made models is lost on stream-out: restart it on stream-in at a believable phase [V] TC23.
- Texture offset scrolling is the cheapest surface motion (water, belts, lava) [V] TC16; flipbooks are at most 8×8 frames at 30 fps and may be switched off on low-memory phones, so the object must still read without them [V] TC17. There is no general animated mesh texture [V] TC18.
- Vary phase or speed per copy (only decorative axes; a meaningful timing never varies); keep ambient motion slower and smaller than anything near a sightline; offer a still or slow variant for players who reduce motion [V] TC29 (the setting exists; the variant is a design choice).

## 7. Rules (final check)
- Never edit the rigger's file, the source snapshot or game code; motion specs go to a builder.
- Never export with Blender defaults (C-13); never rely on a Blender-only deformer, constraint or driver in Roblox (C-12); never key scale for a Roblox clip (C-22).
- Never let a marker or a client's visual state decide gameplay (C-08).
- Never spline before the blocking check-in (with no named reviewer: the recorded self check-in of §3 step 4); never move a frozen key pose or beat frame without a recorded decision.
- Never upload, publish or import into a live place without the brief saying so; tests run in the test place (J005-D6).
- Never write scripts through Studio MCP in `files` source mode (`AGENTS.md` §3); Studio MCP is for import checks, play-tests and captures.
- Never claim a Blender or Studio result without an evidence file from this task; label each check gate-verified / MCP-verified / owner-confirmed / not verified.
- Checks are light (owner J005-D8): numbers for every clip, images only on a failing number plus at most 8 key frames per action (shaded and black-fill from one render pass); plan-stage images keep their own budget (`review.md` §5).
