# Engineering craft: build it right the first time

Most rework in the first game was not hard physics. It was process: tests on toy cases (45 of 159 rounds), no measurement before building (25), "done" without a real check (10), and guesses about the engine (5 tasks). This book is the habits that prevent those, the loop for problems that stay hard even for expert teams, and how to wire what players see and hear so it tells the truth about the game.

## 1. When this skill starts
Any task that writes or changes Luau, content tables that code reads, or place settings. A new system or a refactor starts from the architect's plan (`architecture`); a small, exact change starts at §3 step 1 with every step short. Steps 6 and 8 apply when players see or hear the change (feedback, effects, sound, UI, animation). Step 9 always runs: scale, rejected request, slow server and lifecycles for every change; burst, viewer and quality parts only when players see or hear it. §7 applies to every task. After a context compaction, re-read §3, §6 and §7.

## 3. Steps (cheap stages first; each ends with its check)
1. **Write the behaviour contract** (EC-01), with the brief's target-experience line quoted, the budget (passes or time) and the stop criteria; for every player action, the **feedback stack sheet** (`references/presentation.md` §1). A design answer is missing → `needs-decision` with options and a default. *Check:* SR-01, SR-02.
2. **Read the real code** you will touch and its callers, then the docs mirror page for **every engine system** you touch (EC-02). Search the game for an existing module, effect, cue or component that already does the job before making a new one. *Check:* SR-03.
3. **Engine gate** (EC-03): name the built-in feature for each part. If the design relies on engine behaviour the docs do not state, **probe it** in Studio first (EC-04).
4. **Plan the smallest change**: the files, why each one, what stays untouched (`rules/anti-overengineering.md`); content (values, ids, timings, colours, text) goes in data tables, never in logic (EC-18).
5. **Write the failing case first**, on the real content, data and scale the brief names (EC-09). *Check:* SR-04.
6. **Skeleton pass (playable, ugly, true).** The server rule and its result path run end to end in Studio with obvious stand-ins (plain Parts, a temp cue, a plain label, a placeholder colour), played through the Studio MCP with the real player tools and named in the hand-back. A mechanic the designer judges by behaviour ships first as this skeleton. *Check:* SR-05.
7. **Build.** Strict types, clear names, failures explicit (EC-06, EC-07). For hard-by-nature work, use the loop in EC-05.
8. **Presentation pass** (on the working skeleton): EC-17 to EC-24, in the order of `references/presentation.md` §2-§9, ending with the test hooks and debug log the partners need. *Check:* SR-06 to SR-16.
9. **Worst-case pass.** Real content and scale; the burst rate and the real rate of every frequent event; the most players the brief names; a rejected request and a slow server (the hooks); respawn, reset and reopen 20 times; the lowest quality the brief names (EC-25). *Check:* SR-10, SR-16, SR-17.
10. **Check the exact code**: analyzer, tests, and the Studio run the claim needs (EC-10). Record each check as PASS, FAIL, BLOCKED or NOT RUN; run §6.
11. **Hand back** with the change manifest (EC-13) in the `rules/messages.md` §3 shape: the captures named for each partner's review, the could-not-check list, one named weakness with its next step. *Check:* SR-18, SR-19.

## 4. Craft core
| ID | Practice | Evidence |
| --- | --- | --- |
| EC-01 | **Behaviour contract before code.** Nine fields: existing behaviour; intended change; examples with expected outcomes (one normal, one boundary, one old behaviour that must stay); engine APIs involved; files and callers affected; allowed scope; non-goals; acceptance checks; open design questions. Plus, when players see or hear the result: the feedback stack (EC-17) and the target-experience line it serves. "Make it production ready" is not a contract. A vague brief cost 3-6 rounds per task in the first game | P302, P139; study C06, C11, C12 |
| EC-02 | **Read before writing, docs for every engine system.** Read the implementation and its callers, not file names or a summary. Grep the docs mirror and `_api-reference/classes/<Class>.yaml` for every class, property and enum you use. Missing docs pointers in a brief caused the lighting rework (invented `Bloom` class) | P140, P141; study B08, records SR4 |
| EC-03 | **Engine features first; reuse before new.** Custom game rules are fine; custom **infrastructure** needs a reason. Before you replace an engine mechanism, answer in the hand-back: which built-in you evaluated (docs page), what concrete requirement it failed (with evidence: a probe, a measurement or a docs line), how the replacement will be measured. An emitter property, an Animator priority or a style rule beats code that imitates it. The game's existing modules, pools and effects come before new ones. The first game rebuilt shadows, motion and resting and later deleted or reversed all three | P116, P201; study B09, A07, records SR1; `references/engine-first.md` |
| EC-04 | **Probe what the docs do not say.** When your design depends on engine behaviour the docs leave out (sleep, replication timing, spawn order, stepping, query bounds), run a short Studio probe (`execute_luau` or a play-test, under 30 lines, one question) before you build on it, and cite its output. Every probe the first game ran overruled a guess | old-agents GP3; study A11, A17, B17, E7; `references/probes.md` |
| EC-05 | **Hard-by-nature loop** (physics, destruction, explosions, phone performance). (1) Reproduce with a fixed recipe and record the baseline. (2) Change one thing, named as the one problem this pass solves, the worst first. (3) Measure the same recipe again, 3+ runs, report the spread. (4) Ship new behaviour behind a default-off switch whose off state is byte-identical to the old behaviour, then A/B in Studio before you switch it on. Offline speed-ups were invisible in Studio in the first game; the Studio soak found the real lag cause | study B02, L04, EG9; old-agents HB1; `performance` → `references/measure-loop.md` |
| EC-06 | **Current Luau.** `--!strict` in shared and server code (`AGENTS.md` §2); new client modules too where the API types allow. `unknown` plus refinement (type test, `assert`, equality) over `:: any` or casts; `export type` the public shapes; generics only to keep an input-output relation. Never ship `if local` (Studio beta) or the rolled-back non-type `export`. Native code: server `Script`s, numeric work, measured with and without. Table semantics, iteration order and `const`: `code-review` → `luau-current.md` (read it before writing Luau) | P175-P195; factcheck-engine §3-4 and lead addendum |
| EC-07 | **Clear code shape.** The direct solution with the right data structure; built-ins with the needed meaning (`table.find`, `string.find(s, x, 1, true)`) over hand-written loops. Names carry domain meaning and units (`cooldownSeconds`, `maxStudsPerSecond`). Absence and failure are explicit at the interface (done / denied with a reason / unavailable, `architecture` R-13). Never hide an unexpected error behind a plausible default. There is no universal function length: keep a reader from jumping back and forth, and split only where a name explains a real step | P145, P146, P157-P159, P169, P196 |
| EC-08 | **Validate at boundaries, trust inside.** Client requests, saved data on load, HTTP, failing services get full checks (`networking-security` N-02 order: type, NaN/inf, range, rate, ownership, state). Inside our own code, no defensive checks for states our types and owners rule out | `rules/anti-overengineering.md` 9-10 |
| EC-09 | **Tests on the real thing.** The failing case first (in the first game, a spec that failed before the fix closed the bug in one more round). Then test with the real content table, the real layout or the scale the brief names, not only a toy case: toy-case tests were the biggest single cause of rework. A symptom seen twice gets one shared check, not a second one-off tool | study A05, A14, B05, C16, old-agents FB5, GP4; `testing` skill |
| EC-10 | **Done means checked, on the exact code.** Run the analyzer and the tests on the revision you hand in and read the output. A claim about performance, physics, feel or engine behaviour needs Studio evidence (MCP-verified) or it is `not verified`, and that item is not `done`. Say what each input can prove (§6 inputs). 15 hand-ins in the first game said "Not Studio-verified" honestly and were merged anyway | P147, P151; study A16, B13, C01; `AGENTS.md` §3 |
| EC-11 | **Stop when the API cannot do it.** If the documented API cannot meet the contract, stop that part and return: the unsupported assumption, the probe or docs line that proves it, the smallest alternatives, the player-facing trade-off. Never quietly build a nearby behaviour | P314, P150 |
| EC-12 | **Third patch, stop; rebuild, do not defend.** The same symptom patched a third time means the approach is wrong: stop and return to the architect with the three attempts and what each measured. Code that keeps breaking is rewritten from its contract, not patched again; a better approach from a reviewer replaces yours. In the first game this ended two long patch chains in one design | old-agents FB11, HB8; records B26 |
| EC-13 | **Change manifest** in every code hand-back: requirement ids covered; files changed; public behaviour or API shape changed; dependencies added; test commands with their results; environment (Studio build, Luau version); performance-sensitive paths touched; stand-ins still in place; test hooks added; open questions; what is generated or temporary. The reviewer reads intent from it | P313, P152 |
| EC-14 | **Placement is download size and security.** Server-only code and data in ServerScriptService or ServerStorage; everything under Workspace and ReplicatedStorage replicates to every client. The first game's rule text sent 5.2 MB of stage data and 1.56 MB of server code to every client, and 32k invisible collider Parts replicated | study R02, EG4, EG5; `performance` F-06 |
| EC-15 | **One source for shared lists; scripts for repeated steps.** A list that two places need is derived from one config table, never typed twice; shared registries have one named owner and others ask through a ticket. A manual step you repeat a third time (PROPOSAL) becomes a script or a tool ticket | study C24, C23 |
| EC-16 | **Technical choices are yours; only design forks go to the owner.** Budgets, limits, caps, fallbacks and test design are engineering calls: write them as `PROPOSAL` values and list them in `knowledge/design/open-questions.md` (`AGENTS.md` §0), do not ask them. Ask the owner only where the answer changes what players see or do and no owner decision already answers it, each with a default. One recommendation, never option menus (`rules/owner-profile.md`). An idea that would make it "cooler" mid-job is new scope: a ticket with its cost, never a silent addition | J010 architect scores: 2 of 3 tasks lost on misrouted questions |
| EC-17 | **Feedback follows the confirmed outcome:** the attempt cue answers the input at once on the client; the outcome layer waits for the server's result of that request id; pending when slow; a denial shows its reason, never success | `presentation.md` §2; `architecture` R-05 |
| EC-18 | **One event list; tables, not literals:** no asset id, duration, easing, colour or player-facing string in logic | `presentation.md` §3 |
| EC-19 | **Markers drive presentation; the server clock drives gameplay:** one marker handler for effect and cue, tells sent at wind-up start, drawn areas from the server's data, every hit-stop ends | `presentation.md` §4; R-04 |
| EC-20 | **Draw per viewer:** threats, pickups and own outcome full; others' non-threat effects toned locally; camera and screen channels only for the local player's own events | `presentation.md` §5 |
| EC-21 | **Reduced paths keep the information; never one channel:** one comfort module with five settings (motion, shake, flashes, screen effects, clarity) | `presentation.md` §6 |
| EC-22 | **Frequent events merge and cap; counters tell the truth; refusals say why at the control** | `presentation.md` §7; `ui-basics` U-15, U-16 |
| EC-23 | **Paid reveals are honest in code:** policy module, server roll and commit, one windup chosen without the result, server-sent odds; `platform-policy` wins | `presentation.md` §8 |
| EC-24 | **Test hooks and a debug log ship with the wiring,** in the test build only and Studio-gated; partner reviews depend on them | `presentation.md` §9 |
| EC-25 | **Judge it where players meet it:** play mode, busiest moment, worst-case count, slow and rejecting server, lowest quality; information layers never drop with quality; what looks solid collides | `presentation.md` §10 |

## 5. Rules (final check)
- No custom replacement of an engine mechanism without the EC-03 answer in the hand-back.
- No engine assumption the design depends on without a docs line or a probe result.
- No performance, physics or feel claim marked `done` without Studio evidence.
- No edit to hidden or protected tests, expected results or acceptance fixtures; a wrong test is reported, not worked around.
- No work outside the brief's files; extra problems and "cooler" ideas go in the hand-back as follow-ups with their cost.
- No success layer before the server's confirmation, except a predicted row the spec allows (`references/presentation.md` §2: small, own client, removed on denial; never money, rewards or paid reveals); no attempt cue delayed by a round trip; no gameplay decided by a marker, tween or effect.
- No asset id, duration, colour or player-facing string as a literal in logic.
- No intense channel without its reduced path; no meaning on colour or sound alone.
- No paid reveal whose windup, colour or sound depends on the result before the result frame.

## 6. Self-review before returning (every line names its input)
Inputs: **D** a document (contract, spec, table) · **G** a grep or code read · **A** analyzer and gate output · **T** an offline test · **L** the play-test debug log (`references/presentation.md` §9; script time on one client clock, never output latency) · **S** a Studio state read (`execute_luau`) · **C** a Studio MCP still (at most 6 per feature, the moments the partners named; never proof of timing) · **P** a partner or the owner at a named check-in (feel at normal speed; sound sync on a device capture). Numbers and logs for every case; stills only for failures and named key states. SR-06 to SR-16 apply only when players see or hear the change. Every Studio recipe is a screening aid (false readings: `presentation.md` §11): a failing or borderline reading is checked on the code, the log lines or a still before any fix note.

## 7. Core principles for this craft
The studio's universal principles (master numbers), stated for building features: contracts, Luau, data tables, wiring, tests and Studio checks. Principles 3, 5, 9, 10 and 11 decide what a design shows (read order, shapes, exaggeration, character, style): they belong to the design crafts, and my side of them is to carry their tables exactly (rows 7 and 17).

| # | Principle, for my work | Example from my craft | My check |
| --- | --- | --- | --- |
| 1 | **The gameplay read comes first.** Code never delays, hides or fakes the information players act on; the attempt cue is local and instant, the threat tell is sent when the wind-up starts | A boss slam sent its tell with the damage, so on a 150 ms connection the warning arrived with the hit; the server now fires `slam_tell` at wind-up start | SR-08, SR-13 |
| 2 | **Judge it where players meet it.** Play mode at the game camera, phone viewport, busiest moment, slow and rejecting server; phone cost comes from a phone-class profile with the expected player count (`performance`), never the viewport emulator; unit tests prove rules, never feel | A shop that felt instant on localhost showed nothing for 400 ms under the delay switch until a pending state was added | SR-08, SR-16, EC-25 |
| 4 | **Big before small.** The server rule and the outcome path first, then the event list and the primary layer, then decoration and polish; never polish one screen while the flow is unplayable | The egg shop's hatch animation was wired before purchase failure was handled; the order is now rule, result path, refusal, then reveal polish | SR-05; step order in §3 |
| 6 | **Less is more.** The fewest modules, layers and live instances that carry the read; no one-use abstraction; caps and merges on everything frequent | Twenty coin pickups in a second spawned twenty labels and twenty sounds; one merged label and one cue per window read better and cost less | SR-10, `rules/anti-overengineering.md` |
| 7 | **One code for meaning.** Event ids, cue ids, motion rows, colour tokens and messages each live in one table, and the code reads them | Two screens tweened the same toast with 0.2 s and 0.35 s; both now read the `toast_enter` row | SR-06, SR-07 |
| 8 | **Timing tells cause and effect.** Result after cause; one trigger event for picture and sound; stage timelines in seconds as data, never frames | The coin burst and its tick fired from two remotes and drifted apart under load; both now start in one client handler | SR-08, SR-09 |
| 12 | **Controlled variation, never on meaning.** Random ranges (sample choice, size, rotation) only on fields a spec marks decorative; contact frame, area, fuse, team colour and tier are never randomised | A random start frame on a telegraph flipbook made the same attack look different each time; the field is now locked by the spec's semantic mark | SR-07, SR-13 |
| 13 | **Problem, constraints and target before code.** Contract, feedback stack, engine limits and budget come before the first line | "Make selling feel good" became a contract: attempt tick at once, burst sized by sale tier on `sell_confirmed`, refusal "Backpack empty" | SR-01, SR-02 |
| 14 | **Options, then a reasoned pick.** Before custom infrastructure, the built-in and one cheaper alternative are evaluated and the pick is reasoned in the hand-back; tuning values are exposed so designers can bracket them in Studio | The first game built its own shadow, motion and rest systems and later deleted or reversed all three; the engine-gate answer now names what was compared and why the pick won | EC-03 answer in the manifest |
| 15 | **Cheap stages first; do not be precious.** Skeleton before presentation, presentation before polish; a contract and a spike before the full build; rewrite what keeps breaking | A pet-follow system was proven with grey blocks before any model existed; the third jitter patch was replaced by an `AlignPosition` rewrite | SR-05, EC-12 |
| 16 | **Critique against the goal, one named problem at a time.** Findings name the failure scenario and its evidence; I find the problem behind each note before changing code; one change per measured pass | "Make the hit flash bigger" was really "the flash fires on the server echo, 120 ms late"; moving it to the client fixed the note without a bigger flash | SR-19, EC-05 |
| 17 | **Build for the next craft and the engine.** Tables partners fill, test hooks and a debug log they can read, one root and one scale factor per effect, engine features over imitation | The VFX designer ran the rejected-hit and repetition checks alone because the reject and rate switches already existed | SR-07, SR-10, EC-24 |
| 18 | **Know when it is done.** Stop at the contract's criteria; extra polish and "cooler" ideas are follow-ups with cost | A fourth easing tweak on a menu nobody opens twice went to the follow-up list | SR-01, SR-19 |
| 19 | **Feedback follows the real outcome.** Instant attempt cue; outcome on confirmation sized by its tier; pending when slow; refusal with its reason; true counters; honest reveals | A rejected purchase used to play the coin shower because the client celebrated on send; it now plays the press click and "Need 40 more coins" | SR-08, SR-11, SR-15 |
| 20 | **Every player can read it.** Reduced paths keep every piece of information; no meaning on colour or sound alone; comfort settings change only the local screen | Reduced motion replaced the low-health screen pulse with a steady red edge plus the number, never nothing | SR-14 |
